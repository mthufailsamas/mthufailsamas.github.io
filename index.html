Data engineering & monitoring analytics | Python, PostgreSQL, HTML/CSS/JavaScript

DWDM Optical Sensor Monitoring with Change-Point and Degradation Detection

Problem
Operations teams need a consistent way to separate missing telemetry, short failures, persistent signal shifts, and gradual degradation across a large directional optical-sensor estate.
My Contribution
Implemented the incremental Python/PostgreSQL pipeline, data-quality and failure rules, change-point and degradation analysis, paired-sensor evidence, local API, priority workflow, and browser-based monitoring interface as a Junior Programmer at PT Aplikanusa Lintasarta.
Technical details
Data & Context
Approximately 400 directional sensors combine native 5-minute PRTG optical-power telemetry with ENIMS metadata for sensors, links, directions, endpoints, and locations.
Approach
Built an incremental workflow from metadata synchronization and telemetry collection through failure grouping, PELT change-point detection, Theil-Sen and Mann-Kendall degradation analysis, paired-sensor evidence, priority ranking, and local dashboard delivery.
Validation & Controls
Statistical analysis uses only clean observations. Missing data, downtime, 0 coverage, and low-signal failures remain visible to operations but are excluded from change and trend calculations instead of being filled with invented values.

Project OutputThe pipeline turns raw telemetry into prioritized, traceable investigation views: failure events, persistent downward shifts, gradual degradation, paired-sensor evidence, and dedicated operations, event, and management screens.

Evidence & ScopeThe analysis helps teams decide what to investigate first but does not claim a physical root cause. Internal telemetry, source code, credentials, infrastructure, database contents, and operational screenshots remain confidential.

02

AI/ML engineering & retail forecasting | Python, XGBoost, FastAPI, Docker

Retail Sales Forecasting & Planning System

Problem
Retail planning requires a consistent 16-day view of category demand across 54 stores and 33 product families, while promotions, holidays, transactions, and local operating conditions vary across 1,782 store-family series.
My Contribution
Built the end-to-end system from multi-source preprocessing and forecast-available feature engineering through chronological Ridge/XGBoost evaluation, a versioned model artifact, reusable batch inference, and locally verified FastAPI and Docker delivery.
Technical details
Data & Context
Used 3,000,888 labeled rows from the Kaggle Store Sales competition covering 2013–2017. The prediction contract produces 1 forecast for every date, store, and product-family combination over the next 16 days.
Approach
Compared 3 Ridge settings with 27 XGBoost configurations on a fixed chronological validation window. XGBoost was selected by RMSLE, then the frozen configuration was evaluated in 1 protected internal-test window.
Validation & Delivery
The selected model recorded internal-test RMSLE of 0.4140 and WAPE of 15.6431%. Its versioned artifact generated 28,512 forecasts, while fresh-process batch, local FastAPI, and healthy Docker inference matched the notebook output. All 44 core contract tests also passed in GitHub Actions.

Project OutputThe system produces a checked 16-day forecast for every store-family series, giving planning teams a consistent demand view through the same reusable artifact across batch, API, and containerized inference.

Evidence & Scope1 fixed validation window and 1 protected internal-test window establish RMSLE, WAPE, and signed-bias evidence on 2013–2017 competition data. The locally verified containerized API serves the complete 28,512-row, 16-day product-family forecast through the same versioned artifact used by batch inference.

04

Time-series forecasting | Python, XGBoost, scikit-learn

Rainfall Forecasting with XGBoost and Grid Search

Problem
Daily rainfall is highly variable, and random train-test splits can overstate how well a model will perform on future weather. This project estimates next-day rainfall while keeping evaluation in chronological order.
My Contribution
Built the Python forecasting workflow from data validation and lag construction through XGBoost search, scikit-learn temporal evaluation, and experiment reporting, then authored the resulting peer-reviewed publication as 1st author.
Technical details
Data & Context
Daily BMKG observations from the Trunojoyo observation area in Sumenep Regency combine recent temperature, sunshine, humidity, wind, and rainfall history.
Approach
Created 1-day lagged predictors and searched 243 XGBoost configurations, with Min-Max scaling fitted separately inside each training fold.
Validation & Controls
Used 10-fold TimeSeriesSplit and pooled out-of-fold predictions so every test window followed its training data and future observations did not leak into preprocessing.

Project OutputThe workflow delivers a selected XGBoost model, fold-level results, pooled out-of-fold rainfall predictions, and a traceable experiment report.

Evidence & ScopeThe work became a peer-reviewed publication with Thufail as 1st author. Original BMKG observations remain restricted, so the public repository provides synthetic same-schema data for reviewing and reproducing the workflow.

06

Deep learning & time-series forecasting | Python, TensorFlow/Keras, NumPy, Pandas

Rainfall Forecasting with BiLSTM and Grid Search

Problem
Next-day rainfall depends on changing weather patterns across several recent days, making a sequence-based model more appropriate than treating each observation as an isolated row.
My Contribution
Developed the Python forecasting workflow during my BMKG internship, using NumPy and Pandas for 7-day sequence preparation and TensorFlow/Keras for 3-layer BiLSTM training, focused Grid Search, chronological evaluation, and result reporting.
Technical details
Data & Context
Daily BMKG observations from the Trunojoyo observation area in Sumenep Regency provide 4 weather variables and historical rainfall for each input sequence.
Approach
Built 7-day multivariate sequences, fitted Min-Max normalization on the training period, and trained a 3-layer stacked BiLSTM while tuning units, batch size, and the learning-rate drop period.
Validation & Controls
Used an 80:20 chronological split so every evaluation observation followed the training period. Predictions were returned to millimeters and impossible negative rainfall values were clipped to 0.
0.8073MAAPE
10.2734 mmRMSE
7 daysInput Sequence

Project OutputThe workflow turns 7 days of weather history into next-day rainfall estimates and preserves the selected model, holdout predictions, evaluation summaries, and actual-versus-predicted visual for review.

Evidence & ScopeThe reported BMKG internship results come from 1 chronological holdout period using restricted observations. The public repository includes synthetic same-schema data so the full workflow can still be inspected and run.

07

Statistical time-series forecasting | Python, statsmodels, Pandas

Rice Price Forecasting with ARIMA and Walk-Forward Validation

Problem
Price planning benefits from a forecast that is easy to explain and tested in the same order that future monthly prices would actually become available.
My Contribution
Implemented the Python/statsmodels ARIMA workflow for this collaborative academic project, covering Pandas-based monthly preparation, stationarity checks, order selection, diagnostic screening, expanding-window evaluation, and forecast reporting.
Technical details
Data & Context
60 public monthly observations from January 2020 through December 2024 cover medium and premium rice prices from the Open Data Jawa Timur portal.
Approach
Modeled medium and premium prices separately with ARIMA, using ADF-based differencing, ACF and PACF inspection, candidate evaluation, convergence checks, and residual diagnostics.
Validation & Controls
Started with the initial 80% of observations, forecast the next month, added the newly available actual price, and repeated the process across the remaining 12 months.
2.08%Medium Rice MAPE
1.82%Premium Rice MAPE
12 monthsWalk-Forward Test

Project OutputThe workflow turns public monthly price history into explainable 1-step-ahead forecasts, selected ARIMA orders, diagnostic records, error summaries, and comparison visuals for both rice categories.

Evidence & ScopeThe public data and runnable workflow are included in the repository. The models tracked the evaluated period closely, but rely only on past prices and do not include market events, policy changes, supply, or weather.
